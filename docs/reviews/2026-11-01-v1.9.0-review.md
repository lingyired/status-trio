## 需要修正的问题

### R1 · P2：首次读到的充电还原上限没有保存，重启后可能恢复到 100%

位置：[SettingsStore.swift:1718](../../Sources/StatusTrioCore/Settings/SettingsStore.swift#L1718)，后续取消使用 [ChargeToFullNowController.swift:270](../../Sources/StatusTrioCore/Battery/ChargeToFullNowController.swift#L270)。

没有保存过“取消后还原上限”时，首次启动从系统读到 80%，但初始化赋值不触发 `didSet`，所以 80% 没有落盘。执行“立即充满”后，系统可能清空原策略；此时退出重启，应用重新推导得到 100%，取消时就写入 100%，而不是用户此前的 80%。系统清空策略的实测见[充电研究记录:26](../charge-to-full-now-poc.md#L26)。旧版取消使用持久化 session 的 `originalLimit`，没有这一条新回退。

动态复现：同一个隔离 defaults，第一次 `systemChargeLimit: { 80 }`，第二次 `{ nil }`；实际结果 `80 → 100`。建议首次解析出的还原上限立即持久化，已保存的值始终优先；增加操作期间重启及取消实际使用上限的集成回归。

### R2 · P2：图标未选功耗时，关闭面板仍遗留每 2 秒采样

位置：[StatusPanelViewModel.swift:242](../../Sources/StatusTrioCore/Presentation/Panel/StatusPanelViewModel.swift#L242)。

启用功耗信息栏再打开面板，会登记 `.panel` 和 `.powerInfoBar`。关闭必经 `stop()`，但这里只结束 `.panel`，遗漏 `.powerInfoBar`。即使中心槽没有显示功耗、所有窗口都已关闭，SMC 的 system/input/battery 读取仍每 2 秒继续，直到另一次操作释放需求或退出。

动态复现：图标选择非功耗模式，`start → stop` 后仍有 `demands == [.powerInfoBar]`，`isRunning == true`。建议 `stop()` 同时结束信息栏需求。

用户于 2026-11-01 明确采样边界：图标选择用功耗代替 Wi-Fi 时，即使面板关闭，也必须保留 `.icon` 需求并每 **2 秒**采样；图标未选功耗且所有功耗展示都已关闭时，可以停止或降低采样。本计划选择无需求即停止，沿用现有服务机制。图标仍显示功耗时，关闭面板只释放面板/信息栏需求，不停止或降低图标的 2 秒采样；不再展示的 input/battery 辅助 rails 可停止读取。

### R3 · P2：功耗信息栏开关使用旧值，开启不读数据、关闭反而读数据

位置：[StatusPanelViewModel.swift:206](../../Sources/StatusTrioCore/Presentation/Panel/StatusPanelViewModel.swift#L206)，需求判断位于[同文件:623](../../Sources/StatusTrioCore/Presentation/Panel/StatusPanelViewModel.swift#L623)。

`@Published` 在 `willSet` 时发送新值。订阅丢弃传入的新值，同步回读尚未更新的 `settings.showsBatteryPowerInfoBar`。面板与设置同时打开时，false→true 不登记辅助采样，信息栏缺少输入/电池；true→false 反而保留或启动辅助采样。现有延迟重映射没有重新协调这项需求，要重新开面板或更改分区才纠正。

动态复现：两个方向均失败，调用现有 `ManualPanelUpdateScheduler.runScheduled()` 后仍未纠正。建议将收到的新 Bool 明确传入需求函数；不要引入任意延迟或额外计时器。

### R4 · P2：拔掉电源后，已计算出的电池功耗分解被清空

位置：[BatteryDetailsReader.swift:177](../../Sources/StatusTrioCore/Monitoring/BatteryDetailsReader.swift#L177)。

读取层已支持根据放电功率生成 `.battery` 来源的分解，但 `parse` 使用 `state.isConnected ? breakdown : nil`，在拔电时直接丢弃。展示层又要求拔电状态存在分解才显示图，因此“电池供电时显示功耗流向图”无法走通。现有展示测试直接构造 `BatteryDetails`，绕过了此处。

动态复现：构造通过校验的 30 W 放电分解，经拔电状态 `parse` 后 `breakdown == nil`。建议保留通过新鲜度和来源校验的电池分解；同时禁止从上一帧保留的适配器分解穿越到拔电状态。

### R5 · P2：显示器热插拔未接入亮度清单，保留项也未失效旧 DDC 连接

位置：[BrightnessMonitor.swift:106](../../Sources/StatusTrioCore/Monitoring/BrightnessMonitor.swift#L106)、[同文件:167](../../Sources/StatusTrioCore/Monitoring/BrightnessMonitor.swift#L167)、[同文件:237](../../Sources/StatusTrioCore/Monitoring/BrightnessMonitor.swift#L237)。

没有接入屏幕拓扑变更通知；全仓 `brightnessMonitor.topologyChanged()` 只从 Store 的唤醒路径调用。已有条目时 `refresh()` 只读取旧后端，不重新枚举。保持面板打开再插拔外屏，清单不会及时增删。即使显式调用 `topologyChanged()`，同 ID/后端条目仍直接复用，没有通知 DDC coordinator 丢弃旧 target、旧代请求。

动态复现：保留同 ID 显示器，显式 `monitor.topologyChanged()` 后，coordinator 的 `generation` 不变，也没有重建 coordinator。热插拔通知缺失由全仓调用点静态核实。建议订阅并在停止时清理通知；拓扑更新时重新枚举，并对保留条目失效旧连接及旧代待写请求。

### R6 · P2：DDC 写后读回不匹配时，滑块与错误说明一起消失

位置：[DDCBrightnessCoordinator.swift:230](../../Sources/StatusTrioCore/Display/DDCBrightnessCoordinator.swift#L230)，联动 [BrightnessPanelMapper.swift:12](../../Sources/StatusTrioCore/Presentation/Panel/BrightnessPanelMapper.swift#L12) 和 [BrightnessControlsView.swift:29](../../Sources/StatusTrioCore/UI/BrightnessControlsView.swift#L29)。

首读 30/100，写 70 被 ACK，读回仍为 30/100。解析产生 `scalar=nil` 和 `.unavailable(.writeNotConfirmed)`，但发布时把 `canAdjust` 硬编码为 true。mapper 因 true 不给错误说明，UI 又因 nil 不画滑块，于是只剩显示器名字。

动态复现：fake transport 跑完整首读→写入→读回→mapper，`canAdjust=true`、`unavailableText=nil`。建议失败状态发布 `canAdjust=false`，断言用户能看到不可用说明；不能把 ACK 当作成功。

### R7 · P2：隐藏其他输出设备会让当前 AirPods 的降噪/通透控制消失

位置：[AudioPanelMapper.swift:101](../../Sources/StatusTrioCore/Presentation/Panel/AudioPanelMapper.swift#L101)。

当前 AirPods 仍勾选显示，只隐藏其他输出设备。过滤后只剩一行，且当前设备本身没有被隐藏，于是 `showsDeviceList=false`。这一行虽然带有可操作的 `listeningMode`，但唯一承载降噪/通透控件的输出列表整体不创建；蓝牙区域又会避开已有 CoreAudio endpoint 的重复控件。新版“隐藏不用设备”因此连当前设备的操作一起隐藏。

动态复现：fake endpoint 能解析 AirPods，最终 `rows.count == 1`、`listeningMode.isControllable == true`，却 `showsDeviceList == false`。建议有可操作听音控制的单行仍展示，普通只有一个输出设备且没有听音控制的既有规则保持不变。

### R8 · P2：旧“中间显示电量”偏好在第二次启动丢失

位置：[SettingsStore.swift:1748](../../Sources/StatusTrioCore/Settings/SettingsStore.swift#L1748)。

首次迁移设定内存中的 `.batteryPercentage` 后，直接删除旧 `showsBatteryPercentageInConnectionSlot` key，没有持久化新的 `connectionCenterSource`。初始化不触发 `didSet`。用户升级后不改设置直接退出重开，会回到 `.automatic`，或回到旧的 `.inputSource`。

动态复现：同一个隔离 defaults 连续初始化两次，实际 `.batteryPercentage → .automatic`。建议删除旧 key 前显式保存迁移值，另覆盖旧来源已为 inputSource、迁移后手动改选和再次重启。

## 条件路径问题

### C1 · P2：可选 BetterDisplay 亮度后端丢弃拖动最终值

位置：[BetterDisplayBrightnessCoordinator.swift:127](../../Sources/StatusTrioCore/Display/BetterDisplayBrightnessCoordinator.swift#L127)。

前提是通过配置 API 或已保存的 `externalBrightnessConfigurations.v1` 启用 `.betterDisplay`；当前默认外屏 DDC 和内屏 DisplayServices 不走此分支。

已有 set/get 请求未结束时，后来的 `setBrightness` 直接返回，既不排队也不保存最新值；结束拖动时 monitor 只给 DDC flush。慢请求情况下依次拖到 50% 和 90%，最终可能停在 50%。静态确认此路径，本轮未做 fake 请求动态复现。建议若保留该可选后端，保存最新 pending scalar，旧请求完成后发送末值，stop/切设备时清理。
