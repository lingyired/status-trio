# OPPO / 一加 / realme 耳塞聆听模式接入（交付说明）

日期：2026-11-11
分支：`feat/oppo-listening-mode`

## 结论先行

把 OPPO Enco 系（含一加、realme，同一套 HeyMelody 协议）的**降噪 / 通透 / 关闭**
三模式切换，接进现有聆听模式面板，作为**第四种设备族**（前三种是 AirPods 的
CoreAudio、华为 FreeBuds 的 SPP `0x1101`、红米/小黑的 SPP `FD2D`）。

与红米那族同构：都是 IOBluetooth 的 RFCOMM 厂商通道，只切换耳塞自带的几种模式，
写成功不当作确认，只认设备回报。区别在于 OPPO **没有认证握手**，但模式索引是
**per-model** 的，所以多了一层「型号档案」。

**验证状态**：协议层、会话状态机、型号档案、设备识别、控制器接入均有单测覆盖；
并在 **OPPO Enco X3 真机**上完成了握手、读、写、回读的完整闭环（见第三节实测记录）。

## 协议要点（与本实现一致）

- 链路：SPP。**Enco X3 实测：控制服务在 SDP 里的名字是 `ELNK`，通道 15，没有 `0x1107` 记录**；
  而文档里的 X4 用的是 `0x1107`。所以查找顺序是：`0x1107` 记录 → 服务名含 `elnk` 的记录 → 固定通道 15。
- 帧：`AA | LEN(7bit 变长, LE) | 00 00 | CMD(u16 LE) | SEQ | PLEN(u16 LE) | payload`，
  无校验、无加密。响应 `CMD | 0x8000`，回显 `SEQ`，`payload[0] == 0` 表示成功。
- 握手：`0x0100` → `0x8100 [00][能力位图…]`；随后 `0x0103` 取产品 ID（3 字节小端，
  Enco X4 实测为 `0x06EC10`）。
- 读模式：`0x010C [子类型][01]`，子类型 `1` 当前模式、`2` 长按循环集合、`3` 支持集合；
  答案为 `[00][子类型][类型][掩码 LE…]`，掩码里对应 protocolIndex 的位为 1。
- 写模式：`0x0404 [01][01][掩码…]`，掩码是目标索引的单 bit，最小字节小端
  （索引 ≥ 8 时两字节）；成功回 `0x8404 [00]`，随后设备推送事件 `03 …`。
- 事件：`0x0205 [01][03]` 订阅，用于耳机长按或手机切换后的状态同步。

## 两个关键设计决定

### 1. 索引是 per-model 的，所以有「档案」这一层

`protocolIndex` 的语义随型号变：Enco X4 上 `0` 关闭、`1` 降噪、`2` 通透，`3`…`8`
是关闭/降噪/通透的子档位，`11`…`14` 是自适应。而耳机**永远上报子索引**——选了
「降噪」可能回读 `7`（智能降噪）。

所以：写入用顶层索引（让耳机自己决定档位），回读用别名表归一
（`7` → 降噪、`8` → 通透、`3` → 关闭），UI 只显示三个胶囊。

### 2. 未测量型号靠设备自报，而不是猜

`OppoNoiseProfiles.profile(productID:cycleMask:)` 的规则：

1. 产品 ID 命中测量表 → 用该表（目前已有 Enco X3，PID `0x067410`）；
2. 否则要求设备在长按循环掩码里同时声明索引 `1` 与 `2`
   （即「我能在降噪和通透之间切」）→ 用通用档案；
3. 其余情况返回 `nil`，传输层抛 `unsupportedModel`，面板**不显示任何控件**。

第 3 条是刻意的：只按产品 ID 猜索引，有可能在某个型号上把「降噪」写成「轻度降噪」
或「自适应」，而这种错单测发现不了。宁可不出控件。

### 3. Enco X3 实测记录（2026-11-11）

| 项 | 实测值 |
| --- | --- |
| 控制服务 | SDP 名称 `ELNK`，RFCOMM 通道 15（无 `0x1107` 记录） |
| 握手 | `0x8100`，能力位图 `FF 77 7A EE E6 8F 8E 04` |
| 产品 ID | `0x067410` |
| 长按循环 | `0x010C[02]` = `0x0006`（索引 1、2 = 降噪、通透） |
| 当前模式 | `0x010C[01]` = `0x0010` → **子索引 4**（深度降噪）→ 归一为「降噪」 |
| 事件推送 | 模式变化后收到 `03 01 01 <掩码>` |
| 写入 `0x0404` | 三模式全部成功：回 `0x8404 [00]`，且回读随之变化 |

写入与回读的完整对照（三次写入 + 三次回读，全部实测）：

| 写入（顶层索引） | 发出载荷 | 设备应答 | 回读掩码 | 上报子索引 | 归一 |
| --- | --- | --- | --- | --- | --- |
| `1` 降噪 | `01 01 02` | `0x8404 [00]` | `0x0010` | `4` | 降噪 |
| `2` 通透 | `01 01 04` | `0x8404 [00]` | `0x0100` | `8` | 通透 |
| `0` 关闭 | `01 01 01` | `0x8404 [00]` | `0x0008` | `3` | 关闭 |

**这张表是本次接入最重要的实测结论**：写的是顶层索引（0/1/2），回读永远是子索引（3/4/8）。
因此「写入成功」只能靠**归一后的模式**判定，拿索引比对会把每一次成功都判成失败并回滚 UI。

另外注意写 `0` 关闭、回读报 `3` —— 关闭同样有子索引，别名表里 `3 → off` 不是多余的。

这些字节已经作为固定样本写进 `OppoCapturedEncoX3Tests`，解码器与状态机必须能原样跑通。

## 验证

已通过（离线，无 OPPO 硬件）：

```
swift test --filter Oppo
```

- 40 项测试全绿，覆盖：
  - 帧编码（含 200 字节载荷的变长长度）、每个分片点的重组、噪声/坏帧/假同步重同步、
    2000 段固定种子异常输入不崩溃；
  - 握手 → 产品 ID → 长按循环 → 订阅的完整顺序；
  - 产品 ID 小端解析、子索引归一、歧义掩码（两位同时为 1）不猜；
  - 三模式写入载荷、索引 ≥ 8 的两字节掩码、无档案时不产生写入帧；
  - 写 ack 不当作确认、失败 ack 不触发回读、事件推送更新状态；
  - 型号档案门控（声明/未声明/零掩码）、无 off 索引的档案；
  - `isOppoAudio` 识别（Enco 系、一加/realme 需 buds、非音频、不误判红米华为三星）；
  - 控制器接入：蓝牙行显示、音量行内联、写入确认、失败回滚、不支持型号不显示、
    `stop()` 保留会话 / `shutdown()` 释放、设备离线回收会话；
  - 真机抓包回放（`OppoCapturedEncoX3Tests`）：握手/产品 ID/循环/当前模式的原样字节、
    写入应答 `0x8404 [00]`、以及写 1→报 4、写 2→报 8、写 0→报 3 的三段闭环。

已在 Enco X3 上验收：

- 握手、产品 ID、长按循环、订阅、读当前模式全部按上述顺序走通；
- 长按循环掩码确为 `0x0006`，通用档案与测量表两条路径都能让胶囊出现；
- 写入：三模式全部 `0x8404 [00]`，回读随之变化，归一后与目标一致；
- 事件推送：每次切换都收到 `03 01 01 <掩码>`，且**早于**写入应答到达。

仍待其他型号实测：

- 其他型号的 SDP 是否发布 `0x1107`（X3 没有，改按服务名 `elnk` 解析）；
- 其他型号的子索引布局（X4 文档为 `4…7` 降噪子档、`11…14` 自适应，未在 X3 上验证）；
- 耳机长按切换时事件推送的时延与重复度。

## 怎么测（有硬件时）

1. 配对并连上耳机（名称含 OPPO / Enco）。
2. 打开状态面板的蓝牙区，耳机行下应出现「降噪 / 通透 / 关闭」三胶囊；
   若耳机正作为系统输出，则内联显示在音量行。
3. 点一下切换：胶囊先转圈，设备回报后落在目标模式；若设备没回报，会回滚并短暂标记失败。
4. 若三个胶囊都不出现，优先怀疑两处：SDP 里既没有 `0x1107` 记录、也没有名为 `ELNK`
   的服务（这时才会退回固定通道 15），或设备没在 `0x010C` 子类型 `2` 里声明降噪+通透。

## 已知边界

- 只做三模式切换，不做多档降噪、自适应、EQ、手势、固件升级。
- 采用持久长连接（对齐红米与华为的选择）：耳机连着就一直握通道，关面板不断开；
  释放时机为关闭聆听总开关、应用退出、或耳机断开。
- 型号覆盖面取决于测量表；当前已实测 Enco X3（PID `0x067410`），其余型号靠设备自报的长按循环做能力门控。
- 12 语言设置文案目前只更新了 `en` 与 `zh-Hans`，其余语言待补。
