# 电池面板功率流向与应用能耗排行

在“设置 → 电池显示”中：

- **功耗流向图**：在电池详情页显示输入 / 电池 / 系统功耗流向图，默认开启。原先的“充电器输入、充入电池、系统供电、按部件细分功耗”四个开关已合并为这一个。
- **应用能耗排行**：按最近 60 秒滚动窗口显示最多十个应用的 CPU + GPU 归因估算功率（W），默认展示前五个、可展开其余；GPU 不可用时明确降级为 CPU 能耗，只有 CPU 能耗计数也不可用时才显示 CPU 活跃度百分比。默认关闭。开启后可设置 10–60 秒的后台采样间隔，默认 10 秒。

这些选项作用于电池弹出面板。菜单栏和 Dock 图标共用同一套图标设置与渲染场景；中间槽可以选择显示实时整机功耗，采样由 `PowerSamplingService` 统一持有（各入口统一 2 秒，全部需求结束后停止），详见 [Power in the centre slot](power-center-slot.md)。

## 按部件细分功耗

开启后，同一张流向图把右侧的“系统供电”换成充入电池、显示器、USB 供电、系统这几类支路；USB 供电按端口拆开，每个正在对外供电的口单独一条支路。支路缺失时只隐藏该节点，比例尺不变。

左侧是“当前供电来源”：接电且适配器实际供电（`PDTR` ≥ 5 W）时是充电器输入；适配器空闲或未接电、由电池放电供电时改显示“电池”，此时右侧不再出现“充入电池”，差额按电池放电功率计算。适配器顶到自身上限、负载仍不够时，电池会一边保持“已接电源”一边放电补差额：此时左侧一张卡按瓦数比例分成上下两部分（上为充电器输入，下为电池补电），右侧差额用“适配器输入 + 电池补电”作为总预算计算，流向带仍从整张卡合并流出（issue #396）。

口径与来源（均为只读、同一短连接内读取）：

| 节点 | 来源 | 说明 |
|---|---|---|
| 充入电池 | SMC `B0AC`×`B0AV` | 仅有正向电流时显示；读取失败显示“暂不可用”，不伪造 0 W |
| 显示器 | SMC `PBwo` → `PDBR` → `PBLR` | 内建屏背光功率，不含外接显示器与显示控制器。`PBLR=0` 不作为 0 W 分支；没有实测值时该分支不显示，不做估算 |
| USB 供电（每口一条） | SMC `D1`–`D4` 的 `DnJV`×`DnJI`；这些键无应答时才用 `PowerOutDetails` 的 `Watts`（按 `PortIndex` 分口） | 端口电压×电流。低于 0.20 W 不显示。`PDPowermW` 不做兜底。设备名与充电口见下方“按端口拆分” |
| 系统 | 供电来源 − 充入电池 − 显示器 − USB | 差额，包含 SoC、内存、显示控制器等未单独测量的直流负载；不是传感器读数 |

电池供电时来源读数是放电功率（`B0AC`×`B0AV` 取负值），适配器供电时读 `PDTR`；两者都用同一套差额规则。“系统”是按定义算出来的差额，不读 `PSTR`（本机 `PSTR` 只是晚一个 SMC 周期的 `PDTR`）。差额 < −0.75 W 视为各轨道刷新不同步：保留上一次一致的拆分最多一个刷新周期（6 秒）；仍不一致、缺少输入或充入电池读数、样本过期时，不发布细分，整张图回退为“充电器输入 → 充入电池 + 系统供电”。系统总功耗不会被改名成某个支路。

卡片标签只写「系统」；完整说法「系统功耗（含 SoC）」放在悬停提示与无障碍标签里，详情页右上角的感叹号弹层还会解释这一支路包含哪些负载。

摘要面板电池模块下方的功耗信息栏里那一格 `PSTR` 整机总功耗（含显示器与外设）不能再叫「系统功耗」，否则和本图的「系统」支路同名不同义。它在所有语言里改称「整机功耗 / whole-machine power」之类，与详情页「整机功耗（估算）」统一。

### 显示器功耗与 Issue #374

M3 Air（Mac15,12）没有 `PDBR`，`PBLR` 恒为 0。旧逻辑把 0 当成有效背光并绘制“显示器 0.00 W”。现在的规则：

1. 实测 SMC 背光轨道：新代际先 `PBwo`，再 `PDBR`，最后 `PBLR`；任一读数大于 0.05 W 即使用实测值。
2. 所有实测轨道都缺失或为 0 时，显示器分支不显示，不伪造 0 W，也不使用 `AppleARMBacklight` 估算。
3. 内建屏不在线或已休眠（例如合盖只用外接显示器）时，所有背光轨道都可能保留陈旧的小读数；此时直接隐藏显示器分支。
4. `DISP/DISPEXT` 只代表 SoC 显示控制器，不能冒充背光功率。

SoC 不单独成支路：`PHPC` 是芯片散热估算，覆盖边界未经校准，单独展示会诱导用户把它与输入、分项相加。需要芯片明细时走独立诊断（见 `docs/research/m3-max-macos27-soc-power-research.md`），不与流向图混用。

### 本机实测（Mac15,9 / M3 Max / macOS 27.2，接电、满亮度）

| 读数 | 空载 | 8 线程 CPU 负载 | 亮度 30% |
|---|---|---|---|
| `PDTR` 输入 | 32.4 W | 35–75 W | 21.1 W |
| `PDBR` 显示器 | 8.1 W | 8.1 W | 0.4 W |
| 差额（系统，含 SoC） | 2.8 W | 7–18 W | — |
| `PSTR` 系统 | 32.3 W | 与 `PDTR` 同步 | 21.6 W |
| 参考：`PHPC` 散热估算 | 21.5 W | 15–55 W | — |

- `PDBR` 是内建屏背光读数，不是恒定值：亮度设置不变时仍会随显示内容/背光分区变化（2026-10-30 复测在 3.4–6.5 W 之间摆动）。
- `PSTR` 与上一个 SMC 采样周期的 `PDTR` 逐值相等（本次接电未充电条件下 240/240），因此预算以 `PDTR` 为准，`PSTR` 只用于旧的“系统供电”节点。
- IOReport `Energy Model` 在 macOS 27.2 上仍是冻结的：325 条通道里 324 条 60 秒内计数不变，只有 `GPU Energy` 在增长。计数不变不等于 0 W，所以不用它做支路。
- 无外接设备时 `PowerOutDetails` 不存在；接 USB 扩展坞实测 `Watts=2461 mW`，与端口 `Current × AdapterVoltage` 一致。
- Mac16,1（M4）上 `PowerOutDetails.Watts` 会整段停住（一次停在 4.689 W 超过 8 秒），同一段时间 SMC `D1JV`×`D1JI` 从 4.21 W 降到约 0.05 W。流向图优先用 D1–D4 这八个固定键；键无应答时才退回 `Watts`。低于 0.20 W 的轨是空闲漏电，不画 USB 支路。`PDPowermW` 仍然不用。
- IOReport 的 `DISP`/`DISPEXT` 属于芯片端显示处理，落在“系统”差额里，不能再叠加到“显示器”。
- `PHPC` 仅作为参考保留，不再是流向图支路，也不与任何支路相加。

### 按端口拆分

USB 供电不再合成一个数：每个达到 0.20 W 的通道单独画一条支路，明细列表里再按设备名逐行列出（“USB 供电 · 设备名”），流向卡片太小放不下名字时也能分清是哪根线。左侧输入卡片下方和明细里的“充电接口”行写出适配器插在哪个口（如 MagSafe 3）。

名字和充电口都来自只读 IORegistry，跟着同一次打开详情页的刷新读取，没有额外的观察者或缓存；既没有接电也没有输出时不读：

- **通道 → 端口**：`Dn` 和 `PowerOutDetails.PortIndex` 都按 `PortNumber` 顺序编号到 `Port-USB-C@N` 上（MagSafe、HDMI、SD 卡槽不占通道）。Mac16,1 / macOS 27.3 实测：持续读取 `Port-USB-C@4` 上的总线供电 SSD（约 980 MB/s）时，D3 从 0.85 W 升到 2.7–3.5 W，D1（`@1` 上的 Apple Watch 充电线）和 D2（`@2` 上的显示转接器）不变。这台机器上按 `hpm` 编号排序结果相同，两种规则还没在任何机型上区分开。
- **端口 → 设备名**：`IOUSBHostDevice` 的 `USB Product Name`，经由其主控的 `UsbIOPort` 路径对应到端口。Hub（class 0x09）和 Billboard（class 0x11）不算设备；一个口后面挂多个设备时显示“第一个设备 +N”。
- **充电口**：带 `WinningPowerSourceOption` 的 `IOPortFeaturePowerSource` 所在端口。如果充电器插在某个 USB-C 口上，这个口的通道直接排除，不当成对外供电，不管它读到多少。
- 读到的是 Mac 端口送出的 VBUS 功率。总线供电设备（移动硬盘、手表充电线）就是它的全部耗电；自带电源的设备（显示器、带电源的扩展坞）接近 0；接 Hub 时是整个 Hub 的总和。

只读探测脚本：`scripts/poc/battery-power-rails-readonly.m`（不进入任何 target，不写 SMC、不申请权限）。

## 功率数据与图示


优先读取已有 AppleSMC 只读通道：PSTR（整机）、PDTR（适配器输入），以及 Apple Silicon 上的 B0AC/B0AV（电池电流、电压）。一次刷新共用一个短暂连接，只访问固定键，不扫描或写入 SMC。Apple Silicon 整数电池传感器的 mA/mV 布局经过本机只读探测；Intel 保留原有 AppleSmartBattery 电压、电流回退。

输入传感器缺失时，使用 AppleSmartBattery 的 `PowerTelemetryData.SystemPowerIn`，将 mW 转为 W；电池电压、电流始终来自同一采样来源。基础电池详情继续读取额定功率、循环次数和剩余时间。功率开关关闭后不读取对应新增 SMC 传感器；所有功率关闭时保留原有 15 秒详情刷新，不额外进行快速采样。

适配器额定功率只是能力上限，绝不作为实际输入的替代。所有值都是系统遥测的估算，不是插座侧功率；不同传感器更新时刻不同，三项功率可能不完全相加。未知显示“暂不可用”，不补成 0 W。电源状态不匹配、早于电源切换、过期或未来异常的样本会被丢弃。电池供电时保留原来的净放电功率详情。

接电时，左侧为充电器，右侧为电池与系统。流带共用一个瓦数比例，基准为输入与可见输出合计的较大者。隐藏一个输出后，剩余支路仍按同一比例表示功率；0 W 与未知输入/输出不绘制有厚度的流带。不会为了让图形守恒而改写测量值。

打开电池面板且有功率选项开启时每 2 秒读取，关闭面板即停止。部分机型只能回退到较慢的系统电池遥测，即使重新读取，也可能约一分钟才产生新样本。图形为静态 SwiftUI 路径，无常驻动画。

## 应用能耗排行的口径

开启该选项后，由运行中的应用持有采样：面板关闭时按设置的后台采样间隔读取（默认 10 秒，可选 10–60 秒），详情页打开时固定每 5 秒读取。设置页会明确说明后台采样及暂停条件，修改间隔后立即生效。详情页关闭且后台监测未开启时，会停止采样并释放 IOReport 订阅、GPU client 缓存和 60 秒窗口；后台监测开启时继续按其配置间隔运行。

排行是最近 60 秒滚动窗口的平均估算功率。每个采样区间按实际单调时钟间隔计时，窗口越过 60 秒边界时对跨界样本按重叠时长比例分摊能量。不足 15 秒显示采集中；15–59 秒显示部分窗口并标注采集进度；60 秒后为完整窗口。应用在窗口中途退出时，已测得的区间保留到自然过期。

CPU 能耗来自 `proc_pid_rusage` 的 `RUSAGE_INFO_V6.ri_energy_nj`，PID 复用、启动时间变化、计数回退、过长间隔和睡眠恢复都会重建基线。GPU 部分来自无特权的 `IOAccelerator` 客户端 `accumulatedGPUTime` 与 IOReport `Energy Model` 的 `GPU Energy` 通道；GPU 能量按有效 client GPU 时间比例分配，无法归属的部分保留为未归属桶，不挪给已知应用。`WindowServer` 修正阶段默认关闭，首版只报告原始比例分配。

CPU + GPU 可用时显示「应用能耗 · 最近 1 分钟」的估算 W；GPU 通道不可用、冻结或读取失败时降级为「CPU 能耗」并明确标注；只有 CPU 能耗计数也不可用时才使用 CPU 活跃度百分比。不同量纲不混排。Apple 的公开说明包含 CPU、磁盘 I/O、网络等多个因素，但未给出可直接复刻当前版本的完整公式或阈值；这里不是 Activity Monitor 综合能耗评分的副本。

不启动 `powermetrics`，不申请 root、不扩展 Helper，不读取应用内容、命令行或文档，也不新增常驻高频轮询。

数据口径依据：[Apple XNU Recount](https://github.com/apple-oss-distributions/xnu/blob/main/doc/observability/recount.md) 将 `ri_energy_nj` 定义为 CPU 纳焦能量；[Apple 的电源效率指南](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/MonitoringBatteryUsage.html) 说明原生「使用大量能耗」名单考虑 CPU、GPU、磁盘、网络等多种因素。GPU client 采集思路参考 [Stats](https://github.com/exelban/stats)（MIT）；与 wtop 的原始 GPU 时间比例相比，本实现额外保留未归属桶和归因覆盖率，但不宣称与 wtop 或 TermoBar 数值一致。
