审查版本：本地 `main = 994e0d588ab1dbcb878df68f3b1ee01296faac8e`。公证测试包来自 `a6c5a66b`，两者仅二维码图片不同，功能代码一致。

## 确定的缺口

### F1：高功率状态缺少刷新时机（#235，P2）

现象：首次启用时 Helper 尚未批准，探测可能失败；批准后仍保留失败或不支持状态，直到重新打开面板。面板关闭期间从系统设置改变功率模式，也可能保留旧颜色。

代码证据：[Helper 就绪订阅](../../Sources/StatusTrioCore/Store/SystemStatusStore.swift#L1473)只重新评估低电量自动化，没有刷新高功率状态。现有刷新主要发生在[首次启用](../../Sources/StatusTrioCore/Monitoring/HighPowerModeController.swift#L57)和[打开面板](../../Sources/StatusTrioCore/Store/SystemStatusStore.swift#L1081)。

- [ ] Helper 从不可用或待批准变为可用时，重新读取高功率支持与当前状态。
- [ ] 处理外部功率模式变化，及时更新菜单栏、Dock 和面板，保留原有按需运行边界。
- [ ] 回归覆盖首次探测失败后恢复、Helper 批准、外部切换、关闭功能后停止读取。
- [ ] 真机确认恢复后无需重新打开面板即可显示正确状态。

归因：旧实现已有的生命周期缺口，不是这次重建又删除了代码。

### F2：自动开启低电量后，高功率缓存未同步（#235、#246，P2）

触发场景：应用缓存高功率开启状态，随后低电量自动化开启低电量模式。系统已退出高功率，但应用仍可能显示“高功率模式”；之后关闭低电量模式，又可能错误显示蓝圈。

代码证据：[自动化入口](../../Sources/StatusTrioCore/Store/SystemStatusStore.swift#L1507)只调用低电量 controller；[Helper](../../Sources/StatusTrioPowerHelper/PowerModeService.swift#L67)会同时关闭系统高功率。应用里的高功率缓存没有同步更新，[快捷关闭低电量](../../Sources/StatusTrioCore/UI/BatteryStatusView.swift#L204)也不会刷新另一个 controller。

- [ ] 自动化写入成功后同步两种功率模式的观测状态，失败时保留正确回滚行为。
- [ ] 摘要文案、三态选择器、菜单栏与 Dock 始终反映同一个系统模式。
- [ ] 回归覆盖高功率 → 自动低电量 → 手动关闭低电量，以及写入失败、延迟回读。

归因：旧实现已有的模式协调缺口；不能靠分别测试两个 controller 发现。

### F3：Wi-Fi 权限提示会隐藏电源开关（#252，与 #276 组合，P2）

触发场景：连接 Wi-Fi，但定位未授权、SSID 为空。摘要行显示授权提示后，即使“显示 Wi-Fi 电源开关”设置开启，开关也会消失，失败提示同样受影响。

代码证据：[摘要映射](../../Sources/StatusTrioCore/Presentation/Panel/PanelPresentationMapper.swift#L362)把行意图改为请求授权或打开定位设置；[视图](../../Sources/StatusTrioCore/UI/NetworkStatusView.swift#L23)却只在 `wifiDetails` 意图下显示电源开关。

- [ ] 电源开关的显示条件不再依赖整行是否能进入 Wi-Fi 详情。
- [ ] 未决定、拒绝、受限、已授权四种权限状态下，授权入口与电源操作可以共存。
- [ ] 回归覆盖权限 × 无线电状态 × 显示设置，包括无硬件、关闭后重新开启、失败提示。
- [ ] 真机确认首次安装和拒绝定位后仍可直接操作 Wi-Fi 电源。

归因：本版 #252 的 `4f8e4be1` 与后续 #276 的 `a90bd20d` 组合造成，单项测试没有覆盖组合。

### F4：断连设备的 profiler 旧电量仍直接显示（#248，P2）

已完成：accessory 按 identifier 分组、歧义保护、只对已连接设备回退；附近 BLE 缓存寿命已缩短。

剩余现象：已配对但断连的 AirPods 仍可能显示 macOS 保存的旧电量。修复 accessory 串台不等于所有电量来源的新鲜度问题都已解决。

代码证据：[读取器](../../Sources/StatusTrioCore/Monitoring/BluetoothBatteryReader.swift#L125)仍读取 `device_not_connected` 的电量；Store [直接发布结果](../../Sources/StatusTrioCore/Monitoring/BluetoothDeviceController.swift#L1129)，[呈现层](../../Sources/StatusTrioCore/Models/WiFiNetworkModels.swift#L683)只按地址查值，没有 TTL 或“上次读数”标注。

- [ ] 先确定断连旧电量的处理方式：过期隐藏，或标注“上次读数”；不能当作实时电量。
- [ ] 把确认后的新鲜度策略接到所有相关列表和详情展示。
- [ ] 回归覆盖系统 profiler 保留断连值、连接变化后的旧请求晚到、重新连接后恢复新值。
- [ ] 真机验证两副同型号 AirPods、一副断连和设备离场，分别检查串台与旧电量。

归因：原 issue 提出的剩余验收项，处理方式需要产品取舍；没有证据表明某份已完成实现被重建删除。

### F5：Apple Watch 失败原因没有完整传到用户界面（#249，P2）

已完成：phone/Watch 分组保留、候选裁剪改进、USB 到 network 的补充探测、Swift 诊断模型。

剩余两处接线：

- [原生发现路径](../../Support/MobileBatteryHelper/NativeBatteryClient.m#L369)在创建 companion 或读取 companion identifiers 失败时直接跳过，没有设置失败类别；[Swift 解析器](../../Sources/StatusTrioCore/Monitoring/MobileBatteryHelperReader.swift#L232)即使支持 `failures`，也拿不到原生没有返回的原因。
- [discoveryDiagnostics](../../Sources/StatusTrioCore/Monitoring/AppleDeviceDiscoveryController.swift#L64)只在 controller 内赋值和清理，设置页没有消费，用户无法区分没有 Watch、信任或前置条件不足、companion 服务失败。

- [ ] 原生发现结果区分“正常没有 Watch”和“companion 读取失败”，保留真实错误类别。
- [ ] Swift 侧接收这些错误，设置中提供可理解的原因、前置条件和恢复建议。
- [ ] 回归覆盖真实 native 失败分支，不能只给 mock JSON 填入 `failures`。
- [ ] 真机用已信任的 iPhone + Watch 验证发现和电量读取，并检查不同失败场景的提示。

归因：原生错误上报与 UI 消费没有闭合。现有代码改进不能证明所有 Watch 不显示电量的情况已经修复。

## 需要确认的行为

这些项目暂不按“重建漏搬”处理，确认最终要求后再改代码与 issue 描述。

### A1：低电量自动化周期和支持范围（#246）

- [ ] 确认低电量时用户手动关闭后，短暂插拔电是否允许再次自动开启。原 issue 只允许电量回到阈值以上重置；[当前实现](../../Sources/StatusTrioCore/Monitoring/LowPowerAutoEnableController.swift#L48)在插电时也重置，现有测试明确锁定这个行为。
- [ ] 确认自动化支持范围。当前也受 [高功率平台条件](../../Sources/StatusTrioCore/Store/SystemStatusStore.swift#L1499)限制，仅 Apple Silicon + macOS 26.4+，需要说明是否有意如此。
- [ ] 把独立 `autoLowPowerThreshold` 的后续调整同步到 issue。独立阈值已有提交说明和测试，不应直接按最初“复用颜色阈值”的建议判成遗漏。

### A2：关闭无外网但已关联的 Wi-Fi 是否也确认（#252）

[确认策略](../../Sources/StatusTrioCore/Models/WiFiPowerControl.swift#L14)仅包含 `connected`、`hotspot`，但[状态定义](../../Sources/StatusTrioCore/Models/StatusSnapshot.swift#L55)还把 `noInternet`、`temporary`、`shared` 视为已关联。连接工作内网时关闭可能直接断线。

- [ ] 确认是否扩大到所有已关联状态。原 issue 的细化建议和现有测试本身只列 `connected`、`hotspot`，所以不能直接当成实现漏搬。
