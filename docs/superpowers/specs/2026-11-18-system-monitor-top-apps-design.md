## 1. 目标与已确认范围

基于 `feat/system-monitor-detail-pages`，在 CPU、GPU、内存、网络详情页加入高占用应用列表，让用户能从总体负载直接找到主要来源。每页最多显示 5 个应用，四页均先按应用合并主进程和辅助进程，再排序取前 5。网络在同一行显示实时下载和上传速度。

- 沿用 Stats 的采集方案；不改走以原生进程 API 替换命令的路线。
- 本次先完成设计和实施计划。

## 4. 四类采集与数值口径

### CPU

沿用 Stats 的 `/bin/ps` 和 `-Aceo pid,pcpu,comm -r` 思路，读取所有进程后合并应用，不提前截断。参数必须按独立 argv 正确传递，不通过 shell 拼接。

数值使用 ps 的 `%CPU`，保留它的系统采样/衰减语义；每秒刷新输出不代表精确的最近一秒 CPU 时间差。以单个逻辑核 100% 为口径，多核应用可以超过 100%，例如 240.5%。应用值不能与顶部整机 0–100% 直接相加比较。

### 内存

沿用 Stats 的 `/usr/bin/top -l 1 -o mem -stats pid,command,mem`，取得全部进程的 MEM 值，按应用求和后显示 MB / GB。解析需覆盖字节单位、K/M/G/T、单位换算、末尾的 `+` / `-` 标记、进程名空格和 PID 标记，不能把解析失败当成零。

采用 top MEM 口径，不偷换为 ps RSS。不同进程的共享内存可能重复计数；应用合计是进程 MEM 的汇总，不承诺与详情页总体内存或“应用内存”严格对账。

### GPU

参考新版 Stats：枚举 IOAccelerator 的客户端，从 `IOUserClientCreator` 解析 PID，从 `AppUsage[].accumulatedGPUTime` 获取累计 GPU 时间；以 registry entry ID 保存客户端基线。先算每个客户端的时间差，再汇总至 PID，最终合并为应用。

使用单调时间：`usage = ΔGPUTime / ΔelapsedNanoseconds × 100`。客户端新增、PID 改变、队列数改变、计数器回退或间隔超过正常采样周期的 3 倍时重建相应基线；间隔不足 250 ms 时不产出新值。首次采样显示采集中，第二次有效采样后才排行。缺失字段、不支持或读取失败均不伪造 0%。

设计建议：第一版 GPU 榜单支持实际暴露该字段的 Apple Silicon；Intel 显示不可用。汇总所有可读取加速器客户端，并明确这是应用 GPU 执行时间口径；顶部现有指标仍选最忙设备，两者不强行对账，也不强制将应用结果截到 100%。不使用显存大小替代 GPU 占用。

### 网络

沿用 Stats 的 `/usr/bin/nettop -P -L 1 -n` 思路，使用明确的列选择或排除参数，按表头核对 `bytes_in` / `bytes_out` 后解析。`-P` 只汇总同一 PID 的连接，并不完成应用合并。

逐 PID 保存累计接收、发送字节和进程身份；每次先计算差值并除以实际单调时间间隔，再将各 PID 速度合并为应用。不能直接显示累计字节，也不能假定调用间隔恰好一秒。首次读取仅建立基线，新出现的 PID 同样先建立基线。进程重启、PID 复用、累计值回退、睡眠或超过 3 个采样周期的间隔均重建基线。

设计建议：网络沿用 Stats 的排序方式，以 `max(下载速度, 上传速度)` 降序，次级按 `min(下载速度, 上传速度)` 降序。这样单向高速下载或上传都会进入前列。并列时按稳定应用身份排序。每行同时显示下载和上传，统一使用 B/s、KB/s、MB/s。

nettop 统计连接流量，顶部现有网速来自物理接口；VPN、代理、回环和系统归属可能造成口径差异。不把所有应用速度强行缩放到顶部总量，也不把代理代传流量猜测分摊给其他应用。

## 5. 统一应用归属与 Top 5

处理顺序固定为：读取全量有效进程 → 计算需要基线的 PID 增量 → 解析应用归属 → 按应用求和 → 排序 → 取 5 条。不能先取前 5 个 PID 再合并。

设计建议：

1. 参考 Stats RAM 动态查询 `responsibility_get_pid_responsible_for_pid`；只接受当前仍有效、能解析成运行应用的 owner PID，不把失败结果归到 0 或 -1。该符号是非公开能力，必须按可选能力加载。
2. 用进程可执行路径和主应用路径确认归属；嵌套的 Helper.app / XPC 服务优先归入其外层主应用。符号缺失或 owner 无效时，以可验证的外层应用路径回退。
3. 应用分组以规范化的主 `.app` 路径为身份，bundle ID 辅助校验；不只按显示名分组，不把不同安装路径的同名应用混在一起。
4. 无法可靠归属应用的系统服务或命令行进程保留独立行，以 PID + 启动时间标识，显示真实进程名。不要仅凭父子关系或名字前缀猜归属。
5. 退出进程移除基线和归属缓存；同一个 PID 换了启动时间要视为新进程。无法确认身份时不得复用旧增量基线。图标与应用身份缓存限定于详情会话，退出时释放。
6. 同一应用多个实例合并一行。使用应用名和图标；无法取得图标时显示统一进程占位图标。
7. 只显示有效且正占用的项；少于 5 项时显示实际数量。全为零时显示“暂无活跃应用”，区别于采集中或读取失败。

四类指标采用同一归属器，避免 Chrome 在 CPU 页合并、在网络页拆开的不一致。CPU / GPU / 内存均按应用汇总值降序，并列时按稳定应用身份排序。归属期间发生进程退出属于正常竞态，跳过相应行，不让整个列表失败。采集器自身临时创建的 ps / top / nettop 不参与应用排行。

## 6. 调度、状态和停止路径

设计建议：新增独立的进程榜单服务及叶子 observable，由现有详情页需求驱动；不要把全量 PID 列表塞入整个面板或 Menu Bar / Dock 图标状态，也不让命令阻塞硬件采样队列。内部类型和文件拆分留给实施者。

- 仅当前可见的 CPU / GPU / 内存 / 网络详情页采集对应的一类榜单；概览、磁盘页和面板关闭期间不采集榜单。菜单栏或 Dock 的硬件常驻需求不隐式开启榜单。
- CPU / GPU / 网络默认每秒一次；内存因为 `top` 实测约 0.8 秒/次系统时间，调整为每 3 秒一次，避免详情页打开时持续占用单核。同一榜单最多一个在途采集；以采样开始时间计算下次到期，慢任务不重叠、不补积压 tick、不通过完成回调形成无间隔循环。
- 页面切换、面板关闭、功能关闭、睡眠、服务销毁时，取消调度、终止本服务拥有的子进程、清理基线和缓存。恢复或重新打开后重新采集。
- 每次需求切换增加会话标识，旧结果在返回时必须同时核对会话标识和当前页面，不能回填已经离开的页面。
- ps / top / nettop 用绝对路径和独立参数；固定解析环境。进程执行器同时排空 stdout/stderr，限制输出内存（设计上限 8 MiB）和执行时间（5 秒），避免管道阻塞；超时标记失败，输出越界标记失败，均不能悄悄截断后冒充完整榜单。
- 复用已有 BoundedProcessInvocation 的取消与超时处理：先 terminate，沿用 250 ms 的 kill grace 和 500 ms 的 stream grace，仅处理仍由该执行器持有的子进程；关闭句柄并回收进程。下一轮不能遗留前一轮任务。这是实施计划调研发现既有能力后的内部实现细化，不另造命令执行器。
- 不使用 sudo，不接入特权 Helper，不新增授权弹窗。权限不足时明确显示不可用/失败，不提升权限。

展示状态分别为采集中、有效数据、暂无活跃应用、不支持、读取失败。失败或超时后旧数字不继续冒充实时数据；下一正常采样周期可再读一次，不添加额外重试循环。

## 7. 页面呈现（设计建议）

沿用现有详情页卡片风格，在已有内容末尾增加“高占用应用”卡片；不重排现有总量、曲线和详情字段。CPU / GPU 显示图标、名称、百分比；内存显示图标、名称、内存；网络显示图标、名称、下载、上传两列。最多 5 行。

沿用面板现有滚动与高度约束，保证新增卡片和第 5 行可通过滚动完整查看，不增加嵌套滚动列表。名称单行截断，数值使用等宽数字并保持列对齐；重新排序不触发跳动动画。名称、单位、方向和状态均提供可访问文本。新增文案覆盖全部现有语言。应用 CPU/GPU 百分比独立格式化，保留一位小数且允许超过 100%。

第一版没有点击、右键结束进程或展开进程行为。新榜单不影响图标渲染、现有曲线历史和概览采样口径。

## 8. 验证与验收标准

实施时的测试应验证行为而非镜像实现：

- 同一应用有多个低于单进程 Top 5 的 Helper，合并后可进入应用 Top 5；同名不同应用不误合并，归属失败保留独立项。
- ps / top / nettop 固定样本覆盖空格、特殊字符、单位、缺列、权限错误和非零退出。网络、GPU 的首次采样无伪造占用；正确按真实时间间隔计算。
- PID 复用、计数器回退、GPU 客户端队列变化、长间隔、关闭重开、睡眠唤醒不产生尖峰。
- 关面板和快速切页后采集停止、子进程可回收、迟到结果被丢弃；命令超时不会阻塞现有硬件数据。
- 无占用与不可用状态明确区分；CPU 超过 100% 不截断；Top 5 和网络双列在长名称及不同语言下可读。
- 保留 HardwareMetricsServiceTests、HardwareSamplerTests、HardwareMonitorPanelDemandTests、HardwareDetailTests 相关回归。

开发中走 `bash scripts/test.sh '<受影响过滤器>'`；最终功能交付因涉及状态和并发，执行一次 `bash scripts/verify-local.sh full`。普通测试不启用可见 UI。需要 live UI 时按项目 background-ui-testing 流程另行覆盖。

人工/运行时验收覆盖：多进程浏览器、CPU 负载、GPU 实际负载、下载和上传、VPN/代理场景、快速切页、睡眠恢复；使用已有性能脚本记录设备、基线、采样时长及开关详情页的差异。默认 1 秒采样是否可接受必须有测量；如持续开销过高，应反馈并调整周期，不能把有数据视为性能合格。

macOS 13 与当前 macOS 的运行验证、Apple Silicon 与 Intel 的能力差异分别记录 PASS / FAIL / BLOCKED / NOT RUN。编译通过不等于真机验证。
